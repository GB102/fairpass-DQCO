# Data manifest

Generated by `scripts/11_manifest.py` from the files on disk. Every raw HTTP response is also logged with its URL, UTC fetch time and SHA-256 in `data/cache/provenance.jsonl`. The cache itself is not committed.

## What each kind of value is

| kind | examples |
|---|---|
| **measured** (third-party records) | vetted good/bad outcome of each observation, observation start/end, SatNOGS-recorded max elevation |
| **computed** (deterministic from measured inputs) | SGP4 pass windows and max elevation from stored TLEs, effective station horizons |
| **fitted** | pass-success model parameters and 40 bootstrap replicates (`results/link_model.json`) |
| **simulated** | schedules and their expected delivered data, QAOA output distributions (noiseless and Aer density-matrix noise), LNS traces |
| **hypothetical** | equal mission priority weights (no public priorities exist), fairness weight λ, target K = 2 contacts/day, 60 s re-pointing gap, IonQ-like noise levels |

## Known gaps and caveats

* 'good'/'bad' is a vetting label (signal in the waterfall or decoded data), not a byte count. Only a minority of good observations upload demodulated frames, so frame counts are not used as data volume.
* 'unknown' (not yet vetted) and 'failed' (station/software failure) observations are excluded from the success model. Vetting may be biased towards observations a human looked at.
* Expected data volume uses the transmitter baud rate times pass duration as a link-capacity proxy. Broadcast beacons do not transmit continuously. The sensitivity analysis replaces it with contact time.
* Station configuration (horizon) is a live snapshot. The horizon the scheduler actually used is inferred from each station's own observations.
* Ten European stations were selected by record length and geography, not at random. Results describe this sub-network.
